# Product Thesis v0.1 — Provisional

Status: **PROVISIONAL / EVIDENCE-DERIVED / NOT YET FINAL**

## Target user

Technical practitioners who want to build credible public authority from real technical understanding:

- data engineers
- data architects
- analytics/platform engineers
- ML / AI engineers
- applied AI / agent engineers
- forward-deployed / solutions-oriented technical practitioners

This is **not** a general lifestyle/social-media creator tool.

## Core job

> Turn a technical development, real author expertise, or a broad technical domain into credible educational content backed by primary evidence, explicit author judgment, and proof-bearing artifacts — without inventing experience or flattening every idea into a generic post.

## Product thesis

**Creator Console is an evidence-first technical-authority system, not primarily an AI LinkedIn post generator.**

It helps a practitioner:

1. capture a current development, source, project lesson or broad domain;
2. understand the underlying technical material before drafting;
3. build a claim/evidence graph from appropriate primary sources;
4. collect the creator's actual judgment where the content needs opinion or experience;
5. decide the correct content artifact — single lesson, comparison, architecture teardown, benchmark explanation, question map, ordered series or project-backed build-along;
6. attach proof-bearing artifacts when useful — code, diagrams, evaluations, benchmark tables, checklists or implementation receipts;
7. create platform-native content;
8. independently critique unsupported, generic or misleading output;
9. require exact-content approval before publishing;
10. learn from performance without blindly cloning whatever got the most impressions.

## Differentiation hypothesis

Current creator tools already provide combinations of:

- AI writing and rewriting
- voice profiles
- inspiration / viral-post feeds
- guided interviews
- repurposing
- scheduling
- approvals
- carousels
- analytics

Therefore those capabilities alone are **table stakes**, not our thesis.

The differentiating hypotheses to validate are:

### 1. Claim-level technical provenance

Every externally factual technical claim can be traced to evidence with source class, freshness and confidence.

### 2. Explicit authorship gate

The model may help research and edit, but it cannot manufacture the creator's experience, opinion or production judgment. Opinionated/first-person content requires an `AuthorAssertion` or must remain neutral.

### 3. Technical artifact layer

A technical lesson may include a verified code example, architecture diagram, benchmark/evaluation result, source matrix or implementation checklist. The artifact is part of the content plan, not decorative media added at the end.

### 4. Series and dependency planning

Broad topics are not forced into one post. The system can recommend a question map, prerequisite-aware series, or build-along sequence when the domain requires it.

### 5. Project spine

Where appropriate, a series can accumulate into one concrete technical project so public content also demonstrates depth and implementation skill.

### 6. Evidence semantics

The system distinguishes:

- official/production guidance
- reference implementation
- tutorial/example
- benchmark under stated conditions
- community/practitioner report
- creator-owned experience
- structural inspiration

It must not silently promote one class into another.

## Product boundary

### In scope

- technical source discovery and capture
- source understanding / claim extraction
- evidence and provenance
- creator judgment / authorship capture
- technical editorial strategy
- content-plan selection
- series/question-map/project-spine planning
- proof-bearing artifact planning/generation
- LinkedIn technical lessons
- optional long-form adaptation where the content merits it
- review/critique/revision
- explicit approval
- safe official publishing/export adapters
- content/performance memory tied to meaningful editorial dimensions

### Explicit non-goals

- auto-commenting / engagement bots
- DM automation
- scraping private social data
- viral-post cloning
- impersonating other creators' voice
- invented first-person experience or customer results
- one-click autonomous publishing without explicit approval
- becoming a generic multi-network scheduler
- optimizing solely for impressions/likes
- fake analytics when platform data is unavailable
- treating tutorials/reference servers as production-ready recommendations

## Success test

The product is succeeding when a technical practitioner can start with something like:

- “Snowflake released X”
- “I learned Y during a migration”
- “Teach RAG properly”
- “Here is a paper/repo/post”

and end with a credible artifact whose claims, author perspective, technical proof and publication history are inspectable.

A generated post by itself is **not** sufficient proof of product success.
